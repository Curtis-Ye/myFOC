## 编译失败：main.c 找不到 htim2

- 现象：Keil Build 在 `main.c` 的 `HAL_TIM_Base_Start_IT(&htim2)` 报 htim2 未定义。
- 根因：`tim.c` 已新增 `TIM_HandleTypeDef htim2` 与 `MX_TIM2_Init()`，但 `tim.h` 只声明了 htim1/htim3 和 MX_TIM1_Init/MX_TIM3_Init，漏了 htim2 与 MX_TIM2_Init 原型。main.c 经 `main.h → control.h → FOC.h → tim.h` 间接包含 tim.h，所以 htim1/htim3 可见、htim2 不可见；stm32f1xx_it.c 因自己手写了 `extern TIM_HandleTypeDef htim2;` 而不报错。
- 修复：
  1. `code/Core/Inc/tim.h` 补 `extern TIM_HandleTypeDef htim2;` 与 `void MX_TIM2_Init(void);`
  2. `code/Core/Src/init.c` 的 peripheral_init() 补 `MX_TIM2_Init();`（此前 TIM2 从未初始化，即使编译过了，Start_IT 也会失败或 HardFault）
  3. `code/Core/Inc/stm32f1xx_it.h` 补 `void TIM2_IRQHandler(void);` 声明
- 验证：`D:\Keil_v5\UV4\UV4.exe -j0 -b code/MDK-ARM/myFOC.uvprojx -o build_check.log` → 编译 + 链接通过，**0 Error(s), 0 Warning(s)**；Code=19656 RO=2824 RW=120 ZI=2160，hex 已生成。临时 log 已删除。
- 可用于后续验证的编译命令：`"D:/Keil_v5/UV4/UV4.exe" -j0 -b "E:/运动控制/myFOC/code/MDK-ARM/myFOC.uvprojx" -o <log>`，退出码 0 表示无错误无警告。

## 遗留问题（非编译错误，但会让电机完全不转）

1. `tim.c` 里 `htim2.Init.Period` 与 `htim3.Init.Period` 两行都被注释掉了，全局句柄零初始化 → **ARR=0**，TIM2/TIM3 不会产生预期的更新中断，`HAL_TIM_PeriodElapsedCallback` 里的 FOC 与速度环都不执行。计数频率 = 72 MHz / (71+1) = 1 MHz，故 `ARR = 1 MHz / f - 1`；需按设计频率填回，并与 `control.c` 的 `CTRL_FREQ_HZ=200`、`FOC.h` 的 `FOC_CALL_FREQ=10000` 对齐。
2. `stm32f1xx_it.c` 中 `velocity_control(-3600.0f, g_velocity)` 的 `g_velocity` 在 main.c 定义后从未赋值（`get_velocity()` 调用被注释），速度环反馈恒为 0。
   - 后续用户已改动：Period 填回（TIM2=9999 → 100 Hz，TIM3=124 → 8 kHz），并把 `get_velocity()` 放到 SysTick 里调用，TIM2 回调目标改为 100.0f。上面第 2 条已过时，以下为准。

## 速度闭环电机不动 / g_uq_out 恒 0（只诊断，未改代码）

- 主因：`velocity_updated` 是跨时钟域的"生产者自清"标志，没有握手。
  - 生产：`SysTick_Handler` 每 5 ms（`systick_counter == 5`）调用 `get_velocity()`；该函数开头无条件 `velocity_updated = 0`，只在 `++div_cnt >= VEL_DIV(20)` 的窗口边界置 1 → 每 100 ms 出现一个**仅维持 5 ms** 的高脉冲，同时更新 `g_velocity`。
  - 消费：TIM2 中断 100 Hz（10 ms）里 `velocity_control()` 用 `if (velocity_updated)` 门控 PI 计算。
  - 两个时钟由同一 PCLK 整数分频、相位固定 → 5 ms 脉冲 vs 10 ms 采样，要么每次都命中、要么**永远不命中**（各约 50%）。当前属于后者。
  - 后果：`pid_output` 保持初值 0 → `g_uq_out = uq_from_float(0 * uq_sign(-1)) = 0` 恒成立 → TIM3 中 `FOC_control(g_elec_angle, 0)` 使三相 CCR 全为 ARR/2 ≈ 899（零矢量、线电压 0）→ 电机无力矩。
  - 反证：`g_uq_out = pid_output * uq_sign` 在 if 之外无条件执行，且 `pid_output` 从不清零；只要 PI 命中过一次，g_uq_out 就会保持一个非零常数。"一直为 0" 恰好证明一次都没命中。
- 次要问题（门控修好后仍会转不顺）：速度反馈实际 200/20 = **10 Hz**（注释写 100 Hz / 10 ms 有误，`CTRL_FREQ_HZ/VEL_DIV = 10` 对应 100 ms 窗口）；`g_elec_angle` 只在 TIM2 100 Hz 刷新，而 FOC 在 TIM3 8 kHz 执行，同一角度连用约 80 次；`FOC_CALL_FREQ=10000` 与 TIM3 实际 8 kHz 不符；`current_mode` 从未被置为 USART（usart.c 不写它），TIM3 的 USART 分支为空且目标速度硬编码 100.0f；`g_uq_out`/`pid_output`/`g_elec_angle`/`pid_error` 等中断共享变量未加 volatile。
- 修复方向（待确认后再动代码）：让 `velocity_updated` 由**消费者**清零（置位后保留到 TIM2 取走），或直接在 TIM2 中断里调用 `get_velocity()` 取速度并去掉门控，把测速与 PI 放进同一时钟域。
- 不改代码的调试验证：在 TIM2 分支设断点看 `velocity_updated` / `pid_output`；手动把 `pid_output` 改成 500，若 `g_uq_out` 立刻变 -500 且电机动，说明下游 FOC/PWM 链路正常、断点确实在 PI 门控。

## 方案一实施：velocity_updated 改为消费者清零（已编译验证）

- 用户确认按方案一改。改动 `code/Core/Src/control.c` 4 处 + `code/Core/Inc/control.h` 1 处：

  4. `velocity_control()` 的 `if (velocity_updated)` 内**第一行**加 `velocity_updated = 0;`（先清零再算 PI，缩短被 SysTick 抢占而丢标志的窗口；若在 PI 计算期间被抢占并再次置 1，新标志会保留到下次 TIM2）
  5. control.h 声明注释同步
- 效果：SysTick(5 ms) 置 1 后一直保持，TIM2(10 ms) 最多延迟 10 ms 必能取到；PI 稳定按测速窗口 10 Hz 执行，`pid_output` 不再恒 0。
- 验证：`D:\Keil_v5\UV4\UV4.exe -j0 -b ...` → 编译 + 链接通过，**0 Error(s) 0 Warning(s)**，Code=19664 RO=2824 RW=120 ZI=2160。

## 低速 100 °/s「原地振动不转」诊断（只分析，未改代码）

- 用户已自行把 `VEL_DIV` 20→4（50 Hz / 20 ms 窗口）、`Ki` 0.5→0.1，但 `integral_limit` 仍是 5000。稳态 `pid_output` 上限 = Kp 5×100 + Ki 0.1×5000 = **1000**（满幅 3%），`VEL_UQ_MAX 6000` 从未触及；比改前（Ki 0.5 → 3000）反而小 3 倍。这是我上一轮建议缩 Ki 时未同步放大积分限幅的副作用。静止时推不动齿槽转矩/静摩擦 → 转子在平衡点附近颤。
- `foc_calibrate_phase()`（FOC.c:1172）定义了但**从未被调用**，`phase_sequence` 只赋值从不读取 → 相序校准是死代码；`elec_angle_offset=32.0f` 未实机验证。7 对极下机械角偏 12.9° 即对应 90° 电角度，力矩归零（全 d 轴励磁）→ 转子被吸住振动。
- `g_elec_angle` 只在 TIM2 100 Hz 算，FOC 在 TIM3 8 kHz 用它 → 10 ms 滞后；电压型 FOC 在零速时速度反馈恒 0 → Uq 恒定、电角度由静止编码器决定 → 定子磁场方向固定，转子只会被拉向平衡点，不会自启旋转（低速"零速死锁"）。
- 诊断顺序（调试器）：① 看 `pid_output` 是否稳定在 ±1000 不再增长；② 手动写 `pid_output=4000` —— 立刻转 = 力矩不足，振得更凶但不转 = 电角度/相序错；③ 看 `g_angle_updates` 递增、手拨一圈看 `g_elec_angle` 循环 7 次及 `g_velocity` 符号；④ 打开 `OPEN_LOOP` 跑 `FOC_OpenLoop_Update`（open_loop_Uq=6000）分流硬件/闭环。
- 解决方向：A 力矩（integral_limit→25000 或 Kp→20~30、加 ±1500 静摩擦前馈、VEL_UQ_MAX→12000、VEL_LPF_ALPHA→0.25）；B 方向（开环验证、扫 `elec_angle_offset` 0~51.4°、`uq_sign` 试 ±1、交换任意两相、检查 DRV8313 三个 EN —— gpio.c 只置高 PA1/PA15 两个脚）；C 启动（电角度计算搬进 TIM3 8 kHz、开环强拖 + 速度阈值切闭环）。
- 顺序铁律：**先验方向/零点，再加大力矩**；方向错时加力矩只会振得更凶甚至过流。

## encoder_zeroing() 卡死修复（已编译验证）

- 现象：用户在 main.c 加了 `encoder_zeroing()` 后程序卡死。
- 根因：`delay.c` 的 `delayms()` 用 `static volatile unsigned long delayms_counter` 忙等 `while (0U != delayms_counter)`，但**全工程没有任何地方递减它**（SysTick_Handler 只调 `HAL_IncTick`），所以 `encoder_zeroing()` 第一句 `delayms(1000)` 就无限等待。`FOC.c` 的 `foc_calibrate_phase()` 里 4 处 `delayms` 同样会卡。
- 修复（2 个文件）：
  1. `code/Core/Src/delay.c`：改为基于 `HAL_GetTick()` 的无符号差值忙等（不动 it.c / delay.h，无符号减法天然处理回绕）。
  2. `code/Core/Src/main.c`：把三路 `HAL_TIM_PWM_Start` 提到 `encoder_zeroing()` **之前**（原来校准在 PWM 启动前，`FOC_control` 只写 CCR、MOE 未置位，电机根本不出力，转子不会被拉到零点，读到的偏移量无意义）；校准仍保持在 TIM2/TIM3 `Start_IT` 之前，避免 FOC 中断覆盖 CCR。
- 验证：Keil 编译 + 链接通过，**0 Error(s) 0 Warning(s)**，Code=19768 RO=2824 RW=120 ZI=2160。

## 连带发现（未改，待确认；比前面分析的更靠前）

1. **AS5600_ReadAngle() 致命 bug**（AS5600.c:137）：`last_raw_angle` 是**局部变量**，每次调用重置为 0，`total_machine_angle += (raw_angle - 0)` 累加的是角度**绝对值**而不是增量；`last_raw_angle = raw_angle` 函数返回即丢失。即使转子静止，`current_angle` 也随主循环调用次数高速跳变 → 速度反馈是乱数 → **这才是"原地振动不转"更根本的根因**（此前误以为静止时角度不变）。推荐简化为单圈角度：`((int16_t)raw - (int16_t)machine_angle_offset) & 0x0FFF` × MECHANGLE_COEFFICIENT。
2. `total_machine_angle = UINT64_MAX/2`（mod 4096 = 4095）与 `machine_angle_offset = AS5600_ReadRawAngle()` 在 `%4096` 下并不自洽，校准后角度不会等于 0。
3. `encoder_zeroing()` 只写 `machine_angle_offset`，**不写** `control.c` 的 `elec_angle_offset`（当前 32.0f）。校准改变机械角零点后，32.0°×7 = 224° 电角度偏差会让力矩方向完全错 → 必须把 `elec_angle_offset` 清零或重新扫描标定（0~51.4° 机械角）。
4. 校准期间 PWM 持续输出 `open_loop_Uq=6000` 共 1.6 s，静止无反电动势，注意电机/驱动发热；建议降到 2000~3000 或缩短延时。
5. `encoder_zeroing()` 校准的是机械角零点，不是电角度零点/相序；`foc_calibrate_phase()` 仍是死代码（且内部用 `unsigned short` 接 float 角度）。

## 追加：offset 与 total_machine_angle 不自洽的推导（纯答疑）

- 用户已自行把 `last_raw_angle` 从局部改为全局 `volatile uint16_t`（AS5600.c:33），静止时增量为 0，`total_machine_angle` 保持 T0，偏差是**恒定**的、不再漂移。
- T0 = `UINT64_MAX/2` = 2^63−1 = 0x7FFF…FFFF，低 12 位 = 0xFFF = 4095 → T0 ≡ 4095 (mod 4096)。校准时 total=T0、offset=R，代码返回 `(T0 − R) % 4096 = (4095 − R) % 4096`，而期望 `(R − R) = 0`。例 R=1000 → 3095 LSB ≈ 272°，只有 R=4095 才碰巧为 0。
- 根因：`total_machine_angle` 是「以 2^63−1 为零点的 64 位偏置累计量」，`machine_angle_offset` 是「以 0 为零点的 12 位单圈读数」，两个不同坐标系直接相减。T0 的设计意图（中点当零、防 uint64 下溢）本身没错。
- 自洽三选一：A `total = (T0 & ~0xFFFULL) | raw0`（让偏置低 12 位等于上电读数）；B offset 升级为 uint64，校准时直接记 `offset64 = total`，之后 `temp = (total − offset64) % 4096`；C 去掉累计量，`temp = (raw − R) & 0x0FFF`（推荐）。
- 两个澄清：4096 = 2^12 整除 2^64，故 `(a−b) mod 2^64 mod 4096 = (a−b) mod 4096`，**无符号回绕不是元凶**；跨 0/4096 时差 −4085 ≡ 11 (mod 4096)，模 4096 下自动正确，无需显式归一化。
- 新发现（待确认）：`MECHANGLE_COEFFICIENT = 6.2831854f/4096` 是 **rad/LSB**，返回 0~2π；但 `control.c` 的 `angle_error`（180/360）、`elec_angle_offset=32`、`FOC.c` 的 `angle_reverse`（65536/360）全按**度**用，单位差 57.3 倍。0 点不受影响，但非零角度整条链路会错。
